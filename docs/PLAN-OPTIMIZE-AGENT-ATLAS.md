# 优化计划：从「能跑通」到「高分低成本」（目标版本 0.9.0-beta.3+）

> 存放说明：本计划由 agent-bench 三数据集重测（Run 25/26/27）归因产出；实施方为 agent-atlas 仓库（本文档仅留存于本仓，不在 agent-atlas 本地落地）。

> 来源：2026-11-01 agent-bench 三数据集修复后重测（Run #25/26/27，详见
> `docs/PLAN-FIX-HEADLESS-EVAL.md` 第六节）+ 逐样本判分归因。
> 结论先行：工程可靠性问题（400 / 挂起 / 并发）已修完。当前差距集中在两件事——
> **成本失控**（重型任务单案例累计输入最高 240 万 token）与
> **答案形态不合评分口径**（做了但「说」得不到位、该算的不用计算器）。
> 本计划按「先省钱、再提分、后扩口径」排序，全部改动可用 agent-bench 同口径重测验证。

## 一、数据基线（2026-11-01，deepseek-flash 思考档）

| 指标 | grug-think（Run #25） | GLM-5.2-Agent（Run #26） | glm-5.2-coding（Run #27） |
|---|---|---|---|
| 加权分（5 分制） | 3.629 | 2.608 | 3.182 |
| 通过率 | 25% | 0%（1 条 330s 超时） | 20% |
| 单案例累计输入 token | 4k~91k | 839k~1,055k | 66k~**2,408k** |
| 单案例延迟 | 2~28s | 121~306s | 30~510s |
| 对照：内置单轮 Agent | 4.465 | 3.513 | 4.916 |

调用结构（冒烟实测，2 次工具调用的任务）：共 7 次模型调用 = 主循环 3 + **辅助 4**
（需求分析 1 + 风险评估 2 + 反思 1）。纯 QA 案例固定 3 次调用（分析 + 主循环 + 反思），
辅助占比 2/3。

## 二、问题清单（按 ROI 排序，每条带证据）

### P1 前缀缓存被打断（成本 #1）

- **机制**：`context-builder.ts` 每轮把 memoryNote / skillNote / taskLedger / budgetNote
  拼成第二条 SystemMessage，紧跟 system prompt。其中任何一条变化（技能命中、台账更新、
  预算提示）都会使「system + 注记」之后的内容在 DeepSeek 前缀缓存里失配——
  多步循环每一步的历史都在全量计费，这正是累计输入冲到百万级的主因。
- **证据**：Run #27 #2 累计输入 2,408k token / 案例；`task_usage` 里 cache_read 占比未成规模。
- **方向**：稳定内容前置、易变注记后置——注记从第二条 SystemMessage 挪到
  **最后一条 HumanMessage 的前缀**（或尾部独立 system，需实测网关兼容性），
  让「system prompt + 消息历史」保持字节级稳定，前缀缓存全程命中。
  DeepSeek 缓存命中部分计费约为全价的 1/10，这是收益最大的单项。

### P2 辅助调用占比过高（成本 #2）

- **证据**：调用结构见上表；grug 集每个案例 3 次调用里 2 次是辅助。
- **方向**：
  1. `analyze` 分级：纯 QA / 短指令（消息短、祈使句、寒暄）跳过，直接进主循环；
     需要澄清判断的重任务首轮才跑（决策点 1）。
  2. `review` 分级：仅在涉及工具执行 / 文件改动的轮次启用；无工具轮直接通过。
  3. 辅助节点（analyze / review / 风险评估）换**非思考档轻量模型**：
     `llm.ts` 已支持 per-node runtime，`createWorkflowGraph` 里三个模型实例可分别注入
     `ModelRuntimeConfig`（决策点 2）。思考档的 reasoning 回传也只在主循环需要，
     辅助节点关思考可再省一截输入。

### P3 答案形态不合规（得分 #1）

- **证据**（judge 判分理由原文）：
  - Run #27 #2「回答仅给结构说明和自述验证，**未提供任何代码文件**，核心交付缺失」；
  - Run #27 #5「**未做任何修复、未运行测试**，仅要求用户补充材料」（根因分析却全对）；
  - Run #27 #1「**误称验收文件不存在**并改用自测」；
  - Run #25 #6「输出了大量其他用户名，直接违反要点 2、5」（该精确的不过量、该守格式的没守）。
- **方向**：收尾契约写进 system prompt——最终回答必须包含**交付物清单**：
  产出文件的完整路径、执行过的命令与退出码、测试结果、关键数值结论；
  断言「文件不存在」之前必须先 list_dir / read_file 验证。
  这是纯 prompt 层改动，对 coding 集提分最直接。

### P4 数值不走工具（得分 #2）

- **证据**：Run #25 #7 月供算错（628.51，正确 898.09）——calculator 就在工具清单里没被用。
- **方向**：system prompt 硬规则：一切数值结论必须经 calculator 计算后引用，禁止心算直接给出。

### P5 review 回炉放大（成本 #3 / 延迟）

- **证据**：回炉 = 带 feedback 完整重跑 ReAct，最多 3 次；Run #26 #1 单案例 306s / 1,055k token。
- **方向**：预算感知降级——activeMs / 累计 token 超阈值时 review 强制通过
  （`task-budget.ts` 的 budgetNote 基建已有，补一个硬开关）；
  阈值进 config（如 `REVIEW_BUDGET_GUARD_MS` / `REVIEW_BUDGET_GUARD_TOKENS`）。

### P6 工作区 / 能力声明错配（得分 #3，部分属口径边界）

- **证据**：
  - Run #26 #1：任务语境是 Python 仓库（server.py），Agent 却在 agent-atlas 仓库里做了 TS 改动；
  - Run #27 #5：同样「项目不存在、无法修复」——参考答案基于 HF 数据集原仓库，
    而评测在 agent-atlas 工作区里执行（agent-bench 侧为外部 Agent 提供独立工作区 fixture
    才能根治，属评测系统改造，见 P7）；
  - Run #25 #3：宣称拥有天气 / 邮件 / 房产等工具能力——工具清单里确实注册了 demo 工具，
    但回答场景是「贷款计算助手」，许诺无法兑现的服务构成幻觉扣分。
- **方向**：①开场自检规则——涉及代码修改的任务，第一步先核对目标文件/模块是否存在，
  不存在就在回答里明确「该任务在本工作区不可执行 + 已核对过的证据」，
  而不是迁移语境自行发挥；②能力声明收敛——只声明当前 profile 实际注册的工具能力。

### P7 评测口径升级（agent-bench 侧配合项，本计划只做配合）

- 工具型任务的产出物（文件是否创建、测试是否通过）不进判分；评测工作区与数据集语境错配。
- agent-atlas 侧配合：P3 的交付物清单按**结构化格式**输出（固定小节标题），
  便于评测侧后续解析成「产出物验收维度」。改造主体在 agent-bench，另行计划。

## 五、决策点
